# Administration der Plattformkonfiguration

Die Platform Admin API ist eine interne Control Plane für Tenants, Projekte/Umgebungen, Netzwerke, Asset-Contract-Versionen, Watch-only-Adresspools, RPC-Fähigkeiten, Kursquellen/-richtlinien, Finality-/Matching-Regeln, Quoten, Benachrichtigungsreferenzen, Feature Flags und Wartungsfenster. Private Keys, Seeds, API-Secrets und Credentials werden nie angenommen.

Die API verlangt internes TLS. Der Browser verwendet das Same-origin Admin-BFF; der Assertion-Key gelangt nie zu React. Das BFF prüft Session, Origin/CSRF, MFA und DB-RBAC und signiert eine einmalige Assertion, gebunden an Methode, escaped Path, kanonische Query, exakten Body-Hash, Audience, Ablauf und Nonce. Grants werden nicht aus Browser-JSON übernommen.

Berechtigungen: `platform_config:read|write|request|approve|schedule|activate|rollback|emergency`. Auditor ist read-only; Security Admin erstellt/beantragt Änderungen und führt Notfallaktionen aus; Senior Approver muss eine andere Person sein und genehmigt, plant, aktiviert und erstellt Rollback-Drafts. Tenant-Scopes bleiben strikt.

Workflow: `draft → approval_requested → approved/rejected → scheduled → active`. Aktivierung hängt immutable Snapshot und Historie an und verschiebt nur einen fenced Head. Der Scheduler verwendet `SKIP LOCKED`, begrenzte Leases und monotone Claim Tokens. Rollback ist eine neue Version mit erneuter Genehmigung. Direkte Edits, `PUT` und `PATCH` existieren nicht. Emergency Pause/Resume ist ein separater auditierter Append-only-Stream.

Exakte Beträge und Limits sind dezimale Strings. Chain-spezifische Contracts, Rate-Quorum/Staleness, HTTPS ohne Credentials, Watch-only-Referenzen und Zeitfenster werden validiert. RLS/FORCE, zusammengesetzte FKs, an Path/Body gebundene Idempotenz und eine Audit-Hashkette sichern Scope und Konkurrenz.

Der Rate Worker verwendet weiter `ActiveSnapshotReader`. Vor jedem Zyklus liest der Scanner Chain, Finality, alle RPC-/Asset-Heads, Maintenance und den letzten Emergency Pause atomar über `RuntimeStateReader`. Fehlende, ungefencte, pausierte oder inkonsistente Ressourcen führen zu fail closed; Confirmations werden vom Quorum Head abgezogen und `overlap >= reorg_depth` ist Pflicht. Jeder Commit speichert immutable Snapshot-/Fence-Evidence. `credential_ref` löst nur externe Dateien unter `SCANNER_SECRET_DIR` auf; Production verlangt `SCANNER_PLATFORM_RUNTIME_JSON` im Format `{"chain":"eip155:1","finality":"eip155:1","rpc_providers":["rpc/one","rpc/two"],"assets":["eth-ethereum","usdt-ethereum"],"maintenance":["eip155:1"]}`, statische Konfiguration ist nur für Development/Test erlaubt.

Der Planner prüft Admission in derselben serializable Transaction wie Rate-Tick-Auswahl und Address-Lease. Schlüsselkonvention: Tenant Environment=Merchant-UUID, globale Chain/Finality=Chain-ID, globales Asset=Asset-ID, Tenant Wallet Pool=Wallet-UUID. Alles muss active/current sein; das Tenant-Flag `new_routes` ist zwingend, enabled und auf 10000 bps Rollout. Fehlendes/deaktiviertes Flag, Emergency Pause oder aktives `read_only`/`disable_new_routes`-Fenster lehnen die Route ab. Quote und Assignment speichern Snapshot-IDs/Fences. Matching bleibt im separaten Four-eyes-Workflow; Quota, Notification Channel und Finality finanzieller Sweeps/Refunds sind noch keine Runtime-Consumer.

`platform-outbox-publisher` verlangt eine enabled `outbox_publisher`-Identity, einen fenced Claim, TLS 1.3, mTLS und Bearer-Datei für `/v1/platform-admin/events`. Published wird erst nach exaktem Ack von `event_id` und `claim_token` gesetzt; Redirects/Proxy sind verboten, Health bindet nur Loopback. Echte PostgreSQL-/Provider-/Destination-Tests bleiben Deployment-Admission.
