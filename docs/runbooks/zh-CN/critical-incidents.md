# 重大事件处理流程

## 所有事件的通用控制

1. 确定严重级别、UTC 开始时间、事件指挥、运维负责人、记录员；必要时加入
   安全负责人。只使用一个有审计记录的事件频道。
2. 停止发布、迁移、密钥轮换、回填和人工付款匹配；记录最后正常的镜像摘要
   与配置哈希。
3. 记录环境、受影响租户数、链/资产、时间区间和状态变化。不得在聊天或工单
   中粘贴秘密、完整回调正文、钱包地址或个人数据。
4. 优先采用可逆隔离：移除网关流量、仅将受影响 worker 缩容为零或拒绝其
   egress。不得删除记录、移动扫描游标、强制标记已付款或用临时 SQL 重试回调。
5. 保存健康/就绪状态、Deployment 事件、脱敏日志、队列年龄、提供商区块头、
   数据库状态和发布历史。任何余额/权益修正都要双人复核，并保留受限的追加式 ID 清单。
6. 只有在积压恢复、约束校验、客户补救、告警复测、证据保存和整改负责人确定
   后，才能关闭事件。

## API 或 worker 不可用

1. 对比 `/healthz` 和 `/readyz`。存活但未就绪通常指向数据库或凭据；均失败
   通常指向进程、镜像、调度、内存或节点。
2. 检查期望/就绪副本、重启、PDB、Pending Pod、Secret 键是否存在（不得输出
   值）、连接池、TLS、DNS 和近期 NetworkPolicy 变更。
3. 若由新版本导致，只回滚受影响 Deployment 到已记录的摘要；不得回滚数据库
   模式。数据库完整性存疑时停止写入并执行恢复流程。
4. 逐步恢复流量前，验证就绪、签名请求、幂等创建 intent、结算队列推进，以及
   一次受控回调。

## 扫描器滞后或提供商分歧

本节仅在扫描器通过发布门禁后适用。

1. 将扫描器和结算 worker 缩容为零；已提交事件的回调可继续。不得为追赶进度
   而推进游标或降低 finality。
2. 记录每个 RPC 的身份、chain/genesis、finalized head、最后一致高度的哈希、
   延迟和错误类别。区块浏览器截图或客户收据不是充分证据。
3. 只有在其余真正独立的提供商仍满足 quorum 时才移除异常提供商。找到哈希及
   parent 链在 quorum 下最后一致的高度。
4. 在隔离的对比存储中进行带 overlap 的重扫；核对 transfer 唯一性、合约/mint
   allowlist、decimals、收款地址、日志/内部调用/指令和确认阈值。
5. 先启用 canary shard，再启用结算；观察最老队列年龄和重复。不得自动入账
   unmatched 或仅由 AI 推荐的候选项。

## 链重组

1. 暂停相关链的扫描和结算；记录新旧哈希、共同祖先、深度、quorum 及受影响
   transfer event ID。
2. 判断孤块事件是否越过 finality 并触发账本/权益变更；保留两条历史作为证据。
3. 通过设计好的 reorg/reversal 流程标记孤块 observation。不得删除 observation
   或修改账本；财务修正必须是双人批准、平衡且可关联的补偿交易。
4. 从共同祖先之前重扫并对账后再恢复。向商户提供稳定 event ID 和修复状态，
   不承诺绝对不可逆。

## 回调投递故障

1. 先确认结算正确；回调只是通知，不是事实来源。测量最老待投递项和受影响端点。
2. 检查回调 worker 就绪、租约、DNS/HTTPS egress、证书、响应类别及 envelope key
   可解密性，不得暴露含凭据 URL 或响应正文。
3. 修复边界后让持久队列以原 event ID 和签名重试；不得伪造重复事件或绕过
   SSRF 校验。按端点限速、遵循退避，并验证接收方去重。

## 未匹配付款激增

1. 超过批准基线时停止自动和人工匹配，但保留 ingestion 证据。AI 只能建议，
   不能授权结算。
2. 按链、合约/mint、收款方、transfer 机制、decimals、时间和 route 版本分组；
   检查地址池耗尽及 assignment 到期。
3. 至少使用两个独立 RPC 和智能合约/交易所提现夹具验证标准化。截图不是 proof。
4. 向前修复 parser/route，并重放到对比存储。当前授权操作员可以发起人工 resolution，无需第二名操作员；
   系统仍必须在入账前验证独立节点仲裁、finality、幂等性和唯一转账身份。

## 凭据或密钥泄露

1. 立即视为已泄露，不要求再次发送。向权威源撤销凭据并隔离工作负载；保存
   认证日志、secret audit、网络流、镜像摘要和部署历史，确定可能使用区间。
2. 签发最小权限替代凭据，更新外部 Secret，仅滚动受影响工作负载，并确认旧值
   被拒绝。
3. 不得直接替换 envelope key：必须支持版本化解密，经过验证地重新加密每行，
   并在双人控制下保留回滚密钥。解密能力不确定时先创建快照。
4. 检查未经授权的 intent、resolution、callback 和账本变化；使用补偿流程而非
   删除历史，并按批准的安全/法律流程通知。

## 数据库损坏或 split-brain

1. 移除写流量，停止 API/scanner/workers，并 fence 可疑 primary。绝不能允许两个
   writable primary，也不要反复重启存储节点。
2. 保存数据库日志、WAL、timeline、snapshot、链证据及最后可信 UTC 时间。
3. 恢复到新的隔离数据库，完成对账后受控切换；不得覆盖唯一副本或现场修改行。
