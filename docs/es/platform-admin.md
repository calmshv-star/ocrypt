# Administración de configuración de la plataforma

Platform Admin API es un plano interno para tenants, proyectos y entornos, redes, versiones de contratos de activos, pools watch-only, proveedores RPC, fuentes/políticas de tasas, finality/matching, cuotas, referencias de notificación, flags y ventanas de mantenimiento. Nunca acepta claves privadas, semillas, secretos API ni credenciales.

Solo funciona con TLS interno. El navegador usa el admin BFF del mismo origen; la clave de assertion nunca llega a React. El BFF valida sesión, Origin/CSRF, MFA y bindings RBAC de base de datos, y firma una assertion de un solo uso ligada a método, ruta escapada, query canónica, hash del body exacto, audience, expiry y nonce. Los grants no proceden del JSON del navegador.

Permisos: `platform_config:read|write|request|approve|schedule|activate|rollback|emergency`. El auditor solo lee; security admin redacta/solicita y opera pausas; senior approver debe ser una persona distinta y aprueba, programa, activa y solicita rollback. El scope de tenant no se amplía.

El flujo es `draft → approval_requested → approved/rejected → scheduled → active`. La activación añade snapshots y registros inmutables y solo avanza un head con fence token. El scheduler usa `SKIP LOCKED`, lease acotado y claim token monótono. Rollback crea otra versión y repite la aprobación. No existen ediciones directas, `PUT` ni `PATCH`. Las pausas de emergencia forman un stream append-only separado y auditado.

Importes y límites exactos son strings decimales. Se validan contratos por cadena, quorum y antigüedad de rates, endpoints HTTPS sin credenciales, referencias watch-only y ventanas ordenadas. RLS/FORCE, FKs compuestas, idempotencia ligada a path/body y una cadena hash de auditoría bloquean fugas y carreras.

Rate worker conserva `ActiveSnapshotReader`. Antes de cada ciclo, scanner lee atómicamente chain, finality, todos los RPC/assets, maintenance y el último emergency pause mediante `RuntimeStateReader`. Recursos ausentes, sin fence, pausados o con referencias incompatibles fallan de forma cerrada; confirmations se resta del quorum head y se exige `overlap >= reorg_depth`. Cada rango confirmado guarda evidencia inmutable de snapshot/fence. `credential_ref` solo resuelve archivos externos bajo `SCANNER_SECRET_DIR`; production exige `SCANNER_PLATFORM_RUNTIME_JSON` con estructura `{"chain":"eip155:1","finality":"eip155:1","rpc_providers":["rpc/one","rpc/two"],"assets":["eth-ethereum","usdt-ethereum"],"maintenance":["eip155:1"]}` y el modo estático queda limitado a development/test.

El planner ejecuta admission en la misma transacción serializable que selecciona el rate tick y arrienda la dirección. Claves: environment tenant=UUID de merchant, chain/finality global=chain ID, asset global=asset ID y wallet pool tenant=UUID de wallet. Todo debe estar active/current; el flag tenant `new_routes` es obligatorio, enabled y con rollout de 10000 bps. Un flag ausente/desactivado, emergency pause o una ventana `read_only`/`disable_new_routes` rechazan el route. Quote y assignment conservan IDs/fences. Matching mantiene su workflow four-eyes separado; quota, notification channel y finality de sweeps/refunds aún no son consumidores runtime.

`platform-outbox-publisher` usa una identidad enabled `outbox_publisher`, claim fenced, TLS 1.3, mTLS y bearer desde archivo hacia `/v1/platform-admin/events`. Solo marca published tras un ack con `event_id` y `claim_token` exactos; prohíbe redirects/proxy y expone health solo en loopback. PostgreSQL/providers/destination reales siguen siendo pruebas de admisión de deployment.
