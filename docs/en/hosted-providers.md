# Hosted payment providers

Hosted gateways use the same payment-intent API as on-chain routes. Select the route explicitly: `{"provider":"hosted_gateway","hosted_gateway":{"provider_id":"provider-account-1","asset_id":"usdt-tron"}}`. An on-chain request instead uses `provider=on_chain` and an `on_chain` object. Mixed, legacy, or ambiguous bodies are rejected.

A hosted route returns `provider`, `provider_id`, `provider_reference`, `asset_id`, exact integer `expected_amount_atomic`, and a server-vetted HTTPS `payment_url`. It never invents a receiving address, chain, confirmation count, or transaction hash. The provider creates an immutable fiat-to-asset quote; all conversion operands, rounding-up result, response digest, quote time, and provider reference are stored without floating point.

Provider callbacks are accepted only after bounded raw-body and HMAC verification. The verified body and digests enter an append-only inbox before lifecycle or ledger changes. Duplicate event IDs with identical facts replay safely; changed facts conflict; older events remain evidence without rolling state backward. A callback that arrives before route binding is retained in a bounded pre-bind inbox and replayed after the durable provider order is attached.

The first verified sibling route to settle wins under the payment-intent lock. Other routes are superseded, while late on-chain or provider evidence remains queryable. A callback received while a provider is paused is quarantined and raises a reconciliation incident; it cannot book a ledger entry. Status/reconcile responses may raise incidents but cannot settle funds. Post-settlement refunds also raise incidents; automated refund execution is only an adapter port and remains disabled.

A hosted public payment link redeems without calling the provider inside the link transaction. The transaction reserves one use and creates the intent, checkout capability, immutable provider-create attempt, and preparation job. Checkout reports `preparing_payment_route` with no address or URL until the fenced worker binds a vetted provider route. Replay returns the same capability; expiry or exhausted recovery becomes `payment_route_failed` with a durable incident and never restores link capacity silently.

Production requires PostgreSQL migrations `000016`, `000017`, `000019`, and `000020`, exact runtime grants, external secret-mounted HMAC keys, an admitted provider-operation policy, and API/worker readiness. The same-origin platform-admin cabinet now provides the only supported provisioning and rotation surface: immutable secret-free manifests, write-only external file references, a distinct freshly MFA-authenticated approver, and a private TLS probe whose response and peer-certificate digests are pinned. Activation leaves the provider paused; a new six-operation policy and a separate four-eyes unpause are still required. Legacy rows migrate as `legacy_unadmitted` with no fabricated probe evidence. Do not provision providers with merchant APIs or ad-hoc DB-owner SQL.
