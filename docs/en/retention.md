# Retention and immutable archives

The retention worker is a fail-closed archive data plane. It never deletes business records. It writes deterministic, Ed25519-signed archives to a versioned S3 bucket with Object Lock in `COMPLIANCE` mode, verifies the exact object version, byte length, SHA-256 digest, and retention date, and only then records immutable database evidence.

The closed data classes are `callback_event_body`, `published_outbox_payload`, and `event_history_payload`. Callback bodies and event history are archive-only: current callback replay and merchant event reads still depend on their hot bytes. Only a published outbox payload may be replaced by the `retention-tombstone/v1` forward-schema object, and only when its exact event-history copy exists. IDs, tenant and merchant scope, event type, schema version, sequences, timestamps, original digest, and immutable object reference remain in PostgreSQL.

Pruning needs an effective versioned tenant policy, age eligibility, verified WORM evidence, no active tenant/merchant/record legal hold, no pending delivery or replay dependency, a valid worker lease and fence, and two successful checks separated by the policy grace period. The final SERIALIZABLE transaction repeats every check under the same advisory lock used by legal-hold changes.

The worker requires `APP_ENV=production`, `RETENTION_OBJECT_STORE=s3`, a unique `RETENTION_WORKER_ID`, a dedicated database URL, mounted S3 credentials, and a mounted Ed25519 private key. `/healthz` and `/readyz` are private health endpoints. Readiness fails for missing schema/function grants, Object Lock/versioning admission failure, or stale leases.

Migration 000022 adds the tenant-scoped operator control plane without granting direct table mutation. A policy request records its expected effective version and fence, needs approval by a different operator with fresh MFA, and activates no earlier than its scheduled database time. Callback bodies and event history can never be made prunable; outbox pruning keeps the second-cycle grace check. A lower retention floor is rejected while an active hold or already admitted Object Lock would be weakened.

Legal-hold creation is immediate after `retention:hold_create` authorization and fresh MFA. Its tenant, merchant, or record scope is checked without leaking cross-tenant existence. Release always uses a request and a different fresh-MFA approver, who must also differ from the hold creator. Expiry is an explicit audited worker transition after the database clock reaches `expires_at`; a passed timestamp alone never disables a hold. The browser exposes only bounded case references, lifecycle state, policy digests, batch counts, WORM digests, and tombstone identity. It never receives archived bodies, payloads, object keys or versions, or object-store credentials.

The exact permissions are `retention:read`, `retention:policy_request`, `retention:policy_approve`, `retention:hold_create`, and `retention:hold_release`. `/readyz` fails closed if migration 000022 or any required execution capability is absent. Never grant either the API or worker direct `UPDATE` or `DELETE` on source or retention evidence tables.

Recovery is idempotent: after a lost PUT response, the worker accepts only an exact immutable HEAD result. Version, digest, length, lock mode, or retention mismatch stops acknowledgement and pruning. Database rollback cannot restore a payload already tombstoned; rollback therefore requires retaining migration 000015 while any tombstones exist and restoring from the verified archive through a separately reviewed procedure.
